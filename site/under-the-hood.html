01 — the anatomy

Four layers, one durable foundation

The files are the source of truth. Rules, operators, and surfaces work on top of them and can be replaced without reorganising the vault.

Files

Markdown with YAML frontmatter. Readable by a person, greppable by a script, diffable by git, and portable with nothing but a text editor. There is no export step; the source is already plain text.

Rules

One rulebook the whole system obeys: what may be written where, what has to be approved first, what is archived rather than deleted. Per-runtime adapter files point a given AI tool at that same rulebook. Adding a runtime means adding an adapter; the vault structure stays the same.

Operator

Agent roles, each with a written boundary describing what it may do, what it must never do, and what it escalates. Skills are reusable procedures those roles can run.

Surfaces

Surfaces can be a chat window, an MCP client, a scheduled job, or a web app. They are the most likely layer to change, and the least expensive one to replace.

Why a routing index helps

An agent that has to infer where things live can write to the wrong place. A routing index gives each kind of file a known home, and gives the health check something concrete to compare against when the index goes stale.

02 — the operator layer

A skill has a procedure, parameters, and checks.

The operator layer makes limits explicit: what a public skill contains before it ships, what scheduled loops may process, and which actions wait for approval.

Each public-kit skill, three files

In Cairn’s public catalog, a skill ships with SKILL.md for the procedure, params.md for deployer edits, and checklist.md for acceptance checks, including failure paths and a case where it should not answer. The health check treats a missing file as an error.

Scheduled loops, three caps

For the scheduled loops covered by the kit: an item cap limits batch size, an error cap stops a failing run, and recursion is disallowed. Those limits are loaded by each scheduled skill rather than left to an operator’s memory.

Every write, a gate

Anything that sends or writes outward waits for a human. The wait itself is logged before the action happens, so the record shows intent as well as outcome.

The approval gate that failed first

My first approval gate kept pending approvals in memory with a ten-minute expiry. A restart dropped them silently, my phone never saw them, and the window closed before I could act on anything I hadn’t been sitting in front of. The rebuild made them durable files with a notification on creation, resolvable from anywhere, expiring in seven days.

The practical lesson was simple: if a safeguard adds too much friction, people will find a path around it. The guardrails here are designed to be easy to follow, so they remain part of the working path.

Named roles keep permissions legible

The system uses a handful of named roles with separate boundaries: one ingests, one curates and promotes, one looks for new material, one writes the narrative record, and one keeps the house in order. When something goes wrong, the role and its allowed scope are traceable.

The point is traceability: a bounded actor makes a failure easier to locate.

03 — MDash, the control plane

MDash makes the vault usable day to day

MDash is the local web control plane over the same files: roughly fifty endpoints, a chat surface, retrieval, scheduling, projects, and a usage ledger. The important decisions are operational; they make the system easier to inspect, secure, and recover.

The decisionWhat it prevents
Two API surfaces — an interactive one and a token-authenticated ops one An automation credential wandering into the interactive surface. Automation credentials stay on the ops surface.
The ops surface serves a machine-readable OpenAPI document beside the routes Each harness having to reverse-engineer the machine surface. The spec is reviewed with route changes.
Cross-origin writes blocked once, in middleware, using fetch metadata A new route shipping without the check. Middleware covers the rule as routes are added.
Path containment in two independent layers — sanitise the segment, then verify the resolved path is inside the vault A crafted filename escaping the vault. The second check limits the damage if sanitisation is bypassed.
Writes go to a temp file and get renamed into place A half-written file if the process dies mid-write. The vault only sees the completed rename.
Mailbox handoffs are claimed with an exclusive-create lockfile Two runtimes claiming the same handoff. The filesystem decides which claim wins.
Approvals are files, not rows in memory Losing a pending decision on restart — the failure that taught me the rule.
Every LLM call appends exact token counts; the dashboard estimates spend only where model pricing is known Token use disappearing into a monthly guess. If a cost total is incomplete, the dashboard marks it with a plus sign.
Why token auth came later

The token requirement on the ops surface shipped disabled, with a documented migration path, and was switched on afterwards. Enabling it cold would have broken existing callers, and a hurried recovery could have left the control bypassed. The sequence was part of the security work: keep the migration path working, then require the token.

04 — shared tool schema

One tool schema, two execution paths

MDash exposes the vault to in-app chat and external AI tools. One canonical tool-schema module defines both surfaces: chat binds it to in-process handlers, while MCP binds it to a token-authenticated ops API. They converge on the same vault rules and helpers, but they do not take the same execution path.

One schema, two bindings

The canonical tool-schema module is imported by both the MCP server and the app’s in-process chat layer. Chat binds the definitions to local handlers. MCP binds them to the token-authenticated ops API. A shared schema prevents argument drift while leaving each surface’s execution path explicit.

Shared rules, different paths

Both bindings converge on the same vault rules and helpers. They do not take identical execution paths: the chat loop stays in process, while MCP crosses the token-authenticated ops boundary. That distinction keeps the diagram honest.

When an MCP server earns its keep

If a first-party connector already covers the need, use it. A custom server is another integration to maintain. The useful scoping question is still the plain one: who owns it after go-live?

05 — how it stays honest

Keeping the vault useful

Two loops run on top of each other. The knowledge loop decides what is worth keeping. The improvement loop decides whether a change to the system itself was any good.

Novelty before storage

Findings are checked against what the vault already holds before anything is filed. Duplicates are archived, not stored twice. The point of a second brain is not volume.

Confidence caps on secondhand sources

When a primary source is unreachable, the working alternative is recorded with a cap on how much it can be trusted, so a summary of a summary never gets filed as though it were vendor documentation. Provenance is part of the note, not a footnote.

Monitoring includes blind-spot checks

When a research topic goes quiet, the system checks whether nothing new exists or whether the search method is failing, then recommends a change and flags it. The gap is reported alongside the latest result.

Changes are proposed, tested, then logged either way

The improvement loop doesn’t trust its own suggestions. A proposed change to configuration gets tested before adoption, and the outcome is recorded whether it worked or not — which is the only way the log stays worth reading.

What the health check actually looks for

The quiet rot:

  • a routing index that no longer matches what is on disk
  • a batch that stopped at its cap and was never resumed
  • two notes that have quietly become duplicates
  • a gated action with no matching approval line — the serious one

The last one matters because it means something wrote without waiting. The check reports it without waiting for a manual search.

Why append-only, everywhere

Corrections are new entries, never edits. That costs storage but preserves the audit trail. The vault archives instead of deleting for the same reason: a kept record can be ignored later; a deleted one cannot be recovered.

06 — where it goes next

Six moves from a system that serves one person to one that serves a practice

Sections 01–05 describe the working system and the public kit. Section 06 is the design boundary: work that would need tenant identity, per-client configuration, drift checks, and evaluation before it could support a practice. It is a roadmap, not a claim about current deployment.

Personal north star

The intended loop, with some pieces still ahead.

Perceive → Remember → Know you → Project → Act → Write back

Local semantic recall, signals and taste calibration, and approval-gated actions exist. The fully closed loop and a self-composing surface remain direction. The taste model stays local, and outward writes stay gated.

The gap, said plainly

This is a single-operator system. It authenticates with a static token because there is exactly one person to authenticate. Everything in this section is what would have to change before it belonged in someone else’s environment — and knowing that list precisely is not the same as having built it.

1 · Identity, not a token

The static token becomes federated identity: every action attributes to a person, access is granted by group rather than by secret, and revocation is central and immediate. Approvals route to a role rather than to me, so the gate survives someone being on holiday.

2 · One catalog, many tenants

The skill catalog stays central; each client gets a parameter file. Deploying an existing capability to the next client would mean client-specific configuration plus an acceptance-test run, while the procedure stays in one catalog.

3 · The baseline as a deliverable

Every engagement ends with an approved configuration recorded as files. The drift loop already knows how to compare reality to a baseline; pointed at a tenant, it could turn “is this still how we left it?” into a scheduled answer.

4 · The change feed, pointed outward

The machinery that watches research topics and diagnoses its own blind spots is the same machinery a delivery team needs pointed at vendor release notes and tenant message centres — so a breaking platform change reaches the people who deploy on it before it reaches a client who depends on it.

5 · Evaluation as a regression suite

Acceptance tests already exist per skill. Run the whole set on a schedule and whenever a model version changes, so a model update produces a test result before it reaches a deployment.

6 · Cost as a first-class dimension

The usage ledger records exact token counts per LLM call, and the dashboard estimates spend where model pricing is known. Segmented by client and use case, it could answer the cost question that arrives in month two and guide model selection.

What this points toward

An engagement’s as-built configuration, decisions, approvals, drift findings, and runbooks can all be curated notes with provenance and a date. Put that substrate in the client’s own tenant, where it is already licensed and governed, and the documentation can remain the live record after handover.

This is the same pattern as the mapping page, one level up: the engagement itself gets a durable, inspectable record.

Build it so the next person can operate it, and most of the architecture decides itself.
