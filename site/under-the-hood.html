the long version

Everything above the files is replaceable.

The front board is the short version. This page is the build underneath it: how the vault is actually laid out, what the operator layer enforces, the app and the API surfaces that sit over it, and the parts I got wrong first. It ends with where the pattern goes next — clearly labelled, because that part isn’t built yet.

Written from a system I’ve run daily for about two years. Cairn is the pattern extracted from it, with the personal content stripped out.

01 — the anatomy

Four layers, and only one of them has to survive

Every architectural decision in here comes from one commitment: the files are the truth, and everything that operates on them is a tenant, not a landlord.

Files

Markdown with YAML frontmatter. Readable by a person, greppable by a script, diffable by git, and portable with nothing but a text editor. There is no export day, because there is nothing to export from.

Rules

One rulebook the whole system obeys: what may be written where, what has to be approved first, what is archived rather than deleted. Per-runtime adapter files point a given AI tool at that same rulebook — a new runtime is a new adapter, not a reorganised vault.

Operator

Agent roles, each with a written boundary describing what it may do, what it must never do, and what it escalates. Skills are the verbs those roles use.

Surfaces

Whatever is convenient this year. A chat window, an MCP client, a scheduled job, a web app. Surfaces are the most likely thing to change and the least expensive thing to lose.

Why a routing index instead of search

An agent that has to search for where things live will eventually guess wrong and write to the wrong place. A routing index is a single map file that tells it where each kind of thing belongs, so placement is a lookup rather than an inference. It also gives the health check something to verify against — a stale index is a finding, where a bad guess is just a mess someone finds later.

02 — the operator layer

A skill is a procedure. A boundary is a sentence you can quote back.

The operator layer is where autonomy gets its limits. Two mechanisms carry most of the weight: what a skill has to contain before it ships, and what an agent is allowed to reach.

Every skill, three files

A procedure written in plain language, the parameters a deployer edits, and an acceptance test that includes the failure paths and an I’d-rather-not-answer case. The health check treats a missing one as an error, so an untested skill can’t quietly ship.

Every autonomous run, three caps

An item cap, so a batch can’t run away. An error cap, so a run that has started failing stops instead of grinding. And no recursion — a skill never calls itself. Three limits, written once, loaded by every scheduled skill.

Every write, a gate

Anything that sends or writes outward waits for a human. The wait itself is logged before the action happens, so the record shows intent as well as outcome.

The version that failed, because it is the useful half of the story

My first approval gate kept pending approvals in memory with a ten-minute expiry. A restart dropped them silently, my phone never saw them, and the window closed before I could act on anything I hadn’t been sitting in front of. The rebuild made them durable files with a notification on creation, resolvable from anywhere, expiring in seven days.

The lesson is the part I actually kept: a safety feature that is inconvenient becomes a safety feature people route around. Every guardrail on this page is designed to be cheap to comply with, because the alternative isn’t a stricter system — it’s a bypassed one.

Roles, not one omniscient assistant

The system runs a handful of named roles rather than a single agent with every permission. One ingests, one curates and promotes, one goes looking for new material, one writes the narrative record, one keeps the house in order. Each has a written boundary file, and the boundaries are quotable — when something goes wrong, the question “which role did this and was it allowed to?” has an answer rather than a shrug.

That structure is the same reason least privilege works in a tenant. It isn’t about distrust. It’s that a bounded actor produces a legible failure.

03 — the app over it

Boring choices, made early, in the places that hurt later

The dashboard is a web app over the same files — roughly fifty endpoints, a chat surface, retrieval, scheduling, and a usage ledger. Almost none of what I’d defend about it is a feature. It’s the handful of decisions that decide whether someone else can support it at two in the morning.

The decisionWhat it prevents
Two API surfaces — an interactive one and a token-authenticated ops one An automation credential wandering into the interactive surface. Different auth, different blast radius.
The API spec is generated from the code that serves the routes Documentation drifting from behaviour. Same instinct as as-built docs, enforced by the build instead of by discipline.
Cross-origin writes blocked once, in middleware, using fetch metadata A new route shipping without the check. A control you cannot forget to add beats one you have to remember.
Path containment in two independent layers — sanitise the segment, then verify the resolved path is inside the vault A crafted filename escaping the vault. One layer is a single point of failure.
Writes go to a temp file and get renamed into place A half-written file if the process dies mid-write. The rename is the commit.
Work items are claimed with an exclusive-create lockfile Two agents grabbing the same job. The filesystem arbitrates instead of a race.
Approvals are files, not rows in memory Losing a pending decision on restart — the failure that taught me the rule.
Every operation appends to a usage ledger with an estimated cost and a flag for whether the estimate is measured or inferred A confident wrong number. “What is this costing us” is the month-two question, and an honest range beats a precise fiction.
The one I get asked about most

The token requirement on the ops surface shipped disabled, with a documented migration path, and was switched on afterwards. Enabling it cold would have broken every existing caller, and the fastest route back to working would have been a bypass — which is how a security control becomes a permanent exception. Sequencing is part of the control. I would rather explain a deliberate order than defend an outage.

04 — one definition, many surfaces

The integration decision I’d make again on someone else’s tenant

I built an MCP server so the vault could be operated from more than one AI tool without rewriting the integration each time. Two choices inside it matter far more than the server itself.

One definition, imported twice

The tool definitions live in a single module that both the MCP server and the app’s own chat layer import. Two definitions of the same tools drift, and drift shows up as an agent calling a tool with arguments that work on one surface and fail on the other — a bug that looks like the model misbehaving when it’s actually the plumbing disagreeing with itself.

Every call through the front door

No surface touches the files directly. Everything routes through the authenticated API, so an action taken over MCP is authorised, validated and audited exactly like one taken in the interface. Security and business logic can’t fork by entry point, because there is only one entry point.

And when not to build one

If a first-party connector already covers it, use that. A custom server is code you have signed a client up to maintain, and “we built our own” ages badly the quarter the vendor ships the same thing. The scoping question I’d raise in discovery is the unglamorous one: who owns this after go-live?

05 — how it stays honest

A system that only accumulates is a folder

Two loops run on top of each other. The knowledge loop decides what is worth keeping. The improvement loop decides whether a change to the system itself was any good.

Novelty before storage

Findings are checked against what the vault already holds before anything is filed. Duplicates are archived, not stored twice. The point of a second brain is not volume.

Confidence caps on secondhand sources

When a primary source is unreachable, the working alternative is recorded with a cap on how much it can be trusted, so a summary of a summary never gets filed as though it were vendor documentation. Provenance is part of the note, not a footnote.

Blind spots get raised, not waited on

When a research topic goes quiet, the system distinguishes between “nothing new exists” and “my method for looking is failing,” recommends a change, and flags it. Most monitoring reports what it found. The useful part is being told what you might be missing.

Changes are proposed, tested, then logged either way

The improvement loop doesn’t trust its own suggestions. A proposed change to configuration gets tested before adoption, and the outcome is recorded whether it worked or not — which is the only way the log stays worth reading.

What the health check actually looks for

Not uptime. The quiet rot:

  • a routing index that no longer matches what is on disk
  • a batch that stopped at its cap and was never resumed
  • two notes that have quietly become duplicates
  • a gated action with no matching approval line — the serious one

The last one is the finding that matters, because it means something wrote without waiting. The system names it rather than waiting to be asked.

Why append-only, everywhere

Corrections are new entries, never edits. It costs storage and buys the only thing that makes a log worth having: an audit trail you can edit isn’t an audit trail. The same argument is why the vault archives instead of deleting — you can always ignore a record you kept, and never recover one you didn’t.

06 — where it goes next

Six moves from a system that serves one person to one that serves a practice

Everything above this line is running. Everything below it is design — the honest distinction, kept in the open, because a plan described in the present tense is just a lie with good posture.

The gap, said plainly

This is a single-operator system. It authenticates with a static token because there is exactly one person to authenticate. Everything in this section is what would have to change before it belonged in someone else’s environment — and knowing that list precisely is not the same as having built it.

1 · Identity, not a token

The static token becomes federated identity: every action attributes to a person, access is granted by group rather than by secret, and revocation is central and immediate. Approvals route to a role rather than to me, so the gate survives someone being on holiday.

2 · One catalog, many tenants

The skill catalog stays central; each client gets a parameter file rather than a fork. Deploying an existing capability to the next client becomes configuration and an acceptance-test run — not a rebuild, and not a copy that starts drifting the day it lands.

3 · The baseline as a deliverable

Every engagement ends with an approved configuration recorded as files. The drift loop already knows how to compare reality to a baseline; pointed at a tenant, it turns “is this still how we left it?” into a scheduled answer instead of an annual audit.

4 · The change feed, pointed outward

The machinery that watches research topics and diagnoses its own blind spots is the same machinery a delivery team needs pointed at vendor release notes and tenant message centres — so a breaking platform change reaches the people who deploy on it before it reaches a client who depends on it.

5 · Evaluation as a regression suite

Acceptance tests already exist per skill. Run the whole set on a schedule and whenever a model version changes, and “the model updated” stops being a surprise and becomes a test result. That is the difference between managing an AI deployment and hoping about one.

6 · Cost as a first-class dimension

The usage ledger already records estimated cost per operation and marks whether the number is measured or inferred. Segmented by client and use case, that becomes the answer to the question every engagement gets in month two — and the input to routing cheap work to cheaper models.

The one I find most interesting

Follow the logic far enough and the delivery artefacts and the knowledge system stop being two things. An engagement’s as-built configuration, the decisions behind it, the approvals, the drift findings and the runbooks are all just curated notes with provenance and a date — which is exactly what the vault is for. Put that substrate in the client’s own tenant, where it is already licensed and already governed, and the documentation stops being a deliverable that rots after handover and starts being the live record of the system.

That is the same pattern as the mapping page, aimed one level up: not “here is where the AI’s knowledge lives,” but “here is where the engagement itself lives.”

Build it so the next person can operate it, and most of the architecture decides itself.
