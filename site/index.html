the builder’s corner

What’s behind this board

Cairn is a work sample, not a company. It grew out of a knowledge system I built and use every day. I pared away the personal parts so anyone can run the pattern and inspect the decisions behind it.

  • 69 skills in the source system
  • 5 agent roles with written boundaries
  • 1 custom MCP server, built on Anthropic’s SDK
  • ~50 API endpoints behind one auth layer

The habits that carried into the kit

  • Writes wait for a human. The approval gate exists because my first version failed. Approvals lived in memory with a ten-minute expiry, so a restart dropped them silently and my phone never saw them. What ships in the kit is the redesign: durable files, a notification the moment a request is created, resolvable from anywhere.
  • Nothing is ever deleted. The log is append-only; corrections are new entries. An audit trail you can edit isn’t an audit trail.
  • A skill isn’t a prompt. Every one ships a written procedure, declared parameters, and an acceptance test. Quality stops depending on whether someone typed the right words that day.
  • The system reports its own blind spots. Scheduled checks look for stale indexes, capped batches, and gated actions with no approval line, then raise what they find on their own.

Before the AI work

I ran Microsoft 365 for a ~700-person organization in GCC High, under CMMC and NIST 800-171: identity, permissions, compliance, and training people through change. The taped photo on this board is where that background and the AI work meet.

I know the enterprise constraints, and I’ve built the AI side by hand. This board puts the two in the same place.

the blue sticky, bottom of the board

Ask me how

Openers, if you want to poke at any of it. Every answer is somewhere on this board or in the kit.

  • “How do you stop an agent doing something stupid?” Caps and a gate. Ten items a batch, three consecutive errors and it stops, no skill calls itself, and anything that sends or writes outward waits for a human. The gate exists because my first version failed and dropped approvals on restart.
  • “How is a skill different from a prompt?” Three files instead of one: the procedure, the parameters a deployer edits, and an acceptance test that includes the failure paths and an I-don’t-know case. check.sh treats a missing one as an error.
  • “How would this work in our tenant?” Markdown in a document library, frontmatter as metadata columns, approvals through Power Automate, the log as a list with Purview behind it. Nothing new to buy. The mapping page walks the whole table.
  • “How do you know it still works?” The system reports its own blind spots: stale routing index, a batch that stopped at a cap and was never finished, gated actions with no approval line. It raises them rather than waiting to be asked.
  • “How did you learn all this?” By running it daily and writing down what broke. Every guardrail in the kit traces to a specific failure. The append-only log is what made that possible — you cannot learn from a history you are allowed to edit.

the yellow sticky

Starter kit — running in 10 minutes, no API key

A zip of markdown files and three shell scripts. Unzip it, run init.sh, and a plain POSIX script validates the vault and prints a health report. The first success involves no model, no key and no account. That is deliberate. The structure should hold up before any AI touches it.

$ ./scripts/init.sh
$ ./scripts/check.sh   # exit 0 = healthy vault

The ten-minute claim was tested from a fresh unzip. check.sh refuses to package a broken vault.

the blue sticky

Skill catalog

A skill isn’t a prompt. Every catalog item ships three files: a written procedure, declared parameters, and an acceptance test. Deploying it for the next person is configuration, not rework.

The method comes from the source system, where 69 skills run this way. The kit ships eight of them in generic form: ingestion, curation, health checks, chronicle writing, and the rest of the loop’s moving parts.

The acceptance test is the part that usually gets skipped. It is also the reason a skill survives contact with someone else’s data.

the guardrail stickies

Guardrails

  • Approval gate. Writes wait for a human, and the decision is written to the log before anything happens.
  • Health checks. A stale routing index. A batch that stopped at a cap and was never finished. Two notes that have quietly become duplicates. A gated action with no matching approval line. The vault reports every one of these.
  • One vault, many AIs. Two adapter files sit over one rulebook, so adding a runtime means writing an adapter and leaving your knowledge alone. Curate once, serve every assistant.
  • Hard limits. Autonomous skills carry an item cap and an error cap, so a bad run stops itself early and says where it stopped.

Each of these exists because something went wrong once in the source system, and I wanted the next failure to be loud.

the torn page

The principle

The vault is a pattern, not a product. Your knowledge should outlive your tools.

That is why this site sells nothing. The kit is MIT-licensed markdown and shell scripts, and the mapping page shows the same pattern running on a Microsoft 365 tenant with nothing new to buy. The tools will change next year. The vault will not care.

It is also why this board is a work sample. What is worth showing is the thinking, written down in a form you can run.
