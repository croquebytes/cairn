In your tenant

SharePoint is already a vault.

The vault is a pattern, not a product. Microsoft 365 already ships a file store with metadata, versioning, permissions, and audit. The pattern turns what a tenant already owns into an AI-operable knowledge system. Nothing to buy is the strongest pitch there is.

01 — the mapping

Every part of the vault already has a name here

The landing page carries the short version. This is the whole thing. Read it as a translation rather than a migration. Nothing on the right is a product you have to go and buy.

What this page is not claiming

The kit does not connect to a tenant. Its Microsoft 365 skills run on pasted or exported content today: a copied Teams thread, a downloaded policy, a message-centre item. They are shaped for a tenant, not wired to one.

Wiring them to live data means a Graph app registration, delegated permissions, an admin consent conversation, and a permissions review. That is real work, and this page is not going to describe it as a checkbox.

02 — what you would build with it

Four that earn their keep first

Each one names the vault mechanism it reuses. That is the point. These are not twelve ideas; they are one system pointed at twelve problems.

MSP internal

Per-client engagement vault

Every engagement gets a vault in the client's own SharePoint: discovery notes, an append-only decision log, the as-built, and runbooks that ship as skills. When the delivery engineer changes, the vault is the handoff. Institutional memory that survives turnover.

reuses: the whole loop, plus the decision register
Both

Curate once, serve both

Index the vault through a Graph connector and Copilot and Claude answer from the same curated source. Clients ask "Copilot or Claude?" The vault answer is that this is a runtime choice, not a knowledge choice. The adapter story at tenant scale.

reuses: CLAUDE.md / AGENTS.md adapters, MOC routing
Customer

The living as-built

Deliver as-built documentation as a small vault instead of a PDF. Config changes append to the decision log through a flow, and a weekly lint compares what is documented to what the tenant actually reports through Graph. Drift becomes a scored report instead of a surprise.

reuses: health checks, append-only chronicle, heartbeat
MSP internal

Platform-change watch

Run the standing-topics rotation for the practice rather than for one person: Anthropic releases, Graph changes, the M365 message centre. Each topic carries a last-covered date, and the coverage gaps report themselves. One system watching on behalf of every client environment.

reuses: the scout role, standing topics, ingest

More patterns

Same machinery, different problem.

Ticket → knowledge loop Resolved tickets ingested, novelty-scored against the KB, promoted or archived. Duplicate articles stop accumulating because the gate exists. [Both]
Meeting → decision register Transcripts in; decisions with owners and dates appended to a register list; a weekly digest posted back. Answers "when did we decide that?" [Customer]
Governance evidence vault Approvals, AI-usage logs, policy versions and audit extracts curated append-only in one library. Evidence, not assertions. [Customer]
Onboarding vault for client admins Runbooks shipped as a vault with skills and params, so a new admin inherits a system rather than a PDF. [Customer]
Shared-mailbox triage Shared mailbox → inbox → a classification skill proposes → a human approves in Teams → routed. AI drafts, a human sends, on email. [Customer]
SOW and precedent library Past scopes as knowledge with novelty scoring: have we solved this before, and where. Estimation memory. [MSP internal]
Personal vault in OneDrive Each consultant's second brain inside the tenant, so DLP, retention and legal hold actually apply. The IT-blessable version of "I keep notes in an app". [Both]
Catalog as a SharePoint list Catalog items as list entries with params, checklist, tier and version; deploying to a client becomes a provisioning flow. [MSP internal]
03 — what opens it

The vault doesn’t care what opens it

That is the durability argument made concrete. Markdown in a folder has no opinion about the editor.

Obsidian, pointed at a synced folder

The honest first answer: you don't abandon the tool, you move custody. Same interface, same graph view, same plugins. But the vault now lives where DLP, retention, versioning and backup apply to it.

VS Code

Free, markdown-native, git-aware. The natural fit for technical users, and the editor an AI coding assistant is usually sitting in anyway.

The SharePoint library, directly

.md files with metadata columns, edited in the browser. The no-install answer, and the one that makes the pattern visible to people who will never open a code editor.

Loop and OneNote as human surfaces

Where an organisation already lives in these, a small sync skill normalises pages into markdown in the canonical library. Same adapter pattern as CLAUDE.md and AGENTS.md: one canonical store, thin surfaces over it.

A git repository

GitHub or Azure DevOps, for teams that want pull-request review on knowledge changes. Knowledge with a merge conflict is knowledge someone is paying attention to.

One canonical store

Everything above is a surface. The rule that keeps this from turning into five half-vaults is that exactly one location is canonical, and every other surface syncs into it.

The failure mode

Two canonical stores. It always starts as a convenience and always ends as a reconciliation project.

Where to start

Take one engagement, one shared mailbox, or one policy set. Stand the vault up there, run it for a month, and read the chronicle at the end of it. The pattern either earned its place in that month or it did not, and the log is what tells you which, rather than anyone's impression.
